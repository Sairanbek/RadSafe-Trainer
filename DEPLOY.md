# RST — развёртывание на сервере

[RUNBOOK.md](RUNBOOK.md) — про запуск на своём Mac для разработки. Этот файл — про боевой
сервер в интернете: сайт на своём домене с HTTPS и Telegram-бот, которые работают
круглосуточно и не зависят от того, включён ли Mac.

Всё поднимается одной командой через Docker. Разбираться в Docker для этого не нужно —
достаточно пройти шаги по порядку.

---

## Что получится

Три контейнера, описанные в [docker-compose.yml](docker-compose.yml):

| Контейнер | Что делает |
|---|---|
| `web` | Caddy: отдаёт собранный React-сайт, получает и продлевает сертификат HTTPS, проксирует `/api` на backend |
| `backend` | FastAPI: API сайта и мобильного приложения |
| `bot` | Telegram-бот (long polling, входящие порты не нужны) |

Наружу открыты только порты 80 и 443 — их слушает Caddy. Backend и бот в интернет напрямую
не смотрят.

Обе базы данных лежат в каталоге `data/` на сервере и подключены в контейнеры как том.
**`data/` — единственное, что нужно бэкапить**: контейнеры и код в любой момент
пересобираются из git, а базы — нет.

---

## Что нужно заранее

- **Сервер** с Ubuntu 22.04 или новее, минимум 1 ГБ оперативной памяти. Подойдёт любой
  недорогой VPS.
- **Домен** и **A-запись** DNS, указывающая на IP сервера. Это обязательно **до** запуска:
  Caddy получает сертификат, обращаясь к Let's Encrypt по этому имени, и без работающего
  DNS сертификата не будет.
- **Открытые порты 80 и 443** в файрволе сервера/панели хостинга.
- Заготовленные значения: токен бота от [@BotFather](https://t.me/BotFather), ваш Telegram
  ID, App Password для почты, ключ Gemini. Полный список — в
  [deploy/.env.example](deploy/.env.example).

Проверить, что DNS уже доехал (должен показать IP вашего сервера):

```bash
dig +short rst.example.kz
```

## 1. Установить Docker на сервер

Заходим на сервер по SSH и ставим Docker официальным скриптом:

```bash
curl -fsSL https://get.docker.com | sudo sh
```

Чтобы не писать `sudo` перед каждой командой docker:

```bash
sudo usermod -aG docker $USER
```

После этой команды нужно **выйти и зайти по SSH заново** — иначе новая группа не применится.

Проверка, что всё встало:

```bash
docker compose version
```

---

## 2. Положить код на сервер

```bash
sudo mkdir -p /opt/rst && sudo chown $USER /opt/rst
git clone https://github.com/ВАШ_АККАУНТ/RST.git /opt/rst
cd /opt/rst
```

Дальше **все команды выполняются из `/opt/rst`** — это важно, `docker compose` ищет
`docker-compose.yml` в текущем каталоге.

---

## 3. Перенести банк вопросов

Самый важный шаг, который легко пропустить. **Базы данных не хранятся в git** (они в
`.gitignore`), поэтому после `git clone` вопросов на сервере нет.

`telegram_bot/rst.db` — источник истины по вопросам (~436 штук). Его нужно скопировать
с Mac вручную.

Сначала на сервере создаём каталог:

```bash
mkdir -p /opt/rst/data
```

Затем **на Mac** (в новом окне терминала, не на сервере) копируем базу:

```bash
scp "/Users/sairanbek/Desktop/ПРОЕКТЫ/RST/telegram_bot/rst.db" user@СЕРВЕР:/opt/rst/data/rst.db
```

Здесь `user@СЕРВЕР` — то же, с чем вы заходите по SSH, например `root@203.0.113.10`.

Возвращаемся **на сервер** и отдаём каталог пользователю, под которым работают контейнеры.
Внутри и backend, и бот работают не от root, а от пользователя с uid 10001 (так безопаснее),
и без этой команды они не смогут писать в базу:

```bash
sudo chown -R 10001:10001 /opt/rst/data
```

База сайта `rst_web.db` сюда не копируется — backend создаст её сам при первом запуске
(таблицы заводятся автоматически на старте). Вопросы в неё зальём на шаге 6.

Если сайт уже работал раньше и вы переносите пользователей со старого сервера — скопируйте
и `rst_web.db` в `data/` тем же `scp`, до первого запуска.

## 4. Заполнить секреты

```bash
cp deploy/.env.example deploy/.env
nano deploy/.env
```

Что обязательно заполнить:

- `SITE_ADDRESS` — ваш домен, ровно как в DNS, **без** `https://` и без слэша в конце.
  Например `rst.example.kz`.
- `SECRET_KEY` — подпись токенов входа. Сгенерировать случайный:

  ```bash
  python3 -c "import secrets; print(secrets.token_hex(32))"
  ```

  Скопируйте вывод в файл. Менять это значение потом — значит разлогинить всех
  пользователей разом.
- `BOT_TOKEN` и `ADMIN_ID` — для Telegram-бота.

Остальное (`SMTP_*`, `GEMINI_API_KEY`) можно оставить пустым: сайт запустится, но без почты
не будет работать подтверждение email и сброс пароля, а без ключа Gemini — ИИ-ассистент.

Сохранить в `nano`: Ctrl+O, Enter, Ctrl+X.

Файл `deploy/.env` содержит секреты и в git не попадает — он в `.gitignore`. Не коммитьте
его и не пересылайте в мессенджерах.

---

## 5. Запуск

```bash
cd /opt/rst
docker compose --env-file deploy/.env up -d --build
```

Первая сборка занимает несколько минут — скачиваются образы и собирается фронтенд.
`-d` означает «в фоне»: команда завершится, а контейнеры продолжат работать, в том числе
после того как вы отключитесь от SSH и после перезагрузки сервера (`restart: unless-stopped`).

Смотрим, что всё поднялось:

```bash
docker compose ps
```

У всех трёх сервисов должно быть состояние `running`, у `backend` — ещё и `healthy`
(появляется примерно через полминуты).

Логи, если что-то не так:

```bash
docker compose logs -f          # все сразу, Ctrl+C чтобы выйти
docker compose logs -f backend  # только backend
docker compose logs -f web      # Caddy: тут видно проблемы с сертификатом
```

---

## 6. Залить вопросы на сайт

Backend уже создал пустую базу сайта. Переносим в неё вопросы из банка бота:

```bash
docker compose exec backend python scripts/import_questions.py
```

Должно напечатать `Перенесено вопросов: 436` (число может отличаться). Скрипт идемпотентный —
его безопасно запускать повторно сколько угодно раз.

## 7. Проверить

Открываем `https://rst.example.kz` в браузере — должен открыться сайт с настоящим
сертификатом (замочек в адресной строке, без предупреждений).

Проверка API из командной строки:

```bash
curl -fsS https://rst.example.kz/api/health
```

Ответ `{"status":"ok"}` означает, что цепочка Caddy → backend работает.

Бот проверяется просто: напишите ему `/start` в Telegram.

Заметьте: `/docs` (интерактивная документация FastAPI) наружу намеренно не выставлена — она
описывает всю поверхность API. Как её открыть при необходимости, написано в комментариях
[deploy/Caddyfile](deploy/Caddyfile).

---

## 8. Сделать себя администратором

Админку получает уже существующий пользователь, поэтому порядок такой:

1. Зарегистрируйтесь на сайте обычным образом, через форму.
2. На сервере выдайте себе права:

```bash
docker compose exec backend python scripts/make_admin.py вашpochta@example.com
```

## 9. Расписание: дистракторы и бэкапы

Две вещи стоит запускать по расписанию. Открываем crontab:

```bash
crontab -e
```

и добавляем две строки:

```
0 4 * * * cd /opt/rst && docker compose --env-file deploy/.env exec -T backend python scripts/daily_distractor_job.py >> /opt/rst/data/cron.log 2>&1
30 3 * * * cd /opt/rst && docker compose --env-file deploy/.env exec -T backend python scripts/backup_db.py >> /opt/rst/data/cron.log 2>&1
```

Что это делает:

- **04:00 — порция дистракторов.** `daily_distractor_job.py` перегенерирует неверные варианты
  ответов через Gemini и сразу импортирует результат на сайт. Порция намеренно небольшая:
  дневная квота Gemini (~20 запросов) общая на весь проект, и её делят офлайн-генерация и
  живой ИИ-ассистент. Подробности и как ускорить — в шапке самого скрипта.
- **03:30 — бэкап базы сайта.** Кладёт снимок в `data/backups/`, хранит последние 14 и сам
  удаляет старые. Снимок делается через SQLite API, поэтому безопасен даже если backend в
  этот момент пишет в базу.

Флаг `-T` обязателен: у cron нет терминала, и без него `docker compose exec` падает.

Посмотреть, что задания отрабатывают:

```bash
tail -50 /opt/rst/data/cron.log
```

Проверить прогресс перегенерации дистракторов вручную, не тратя квоту:

```bash
docker compose exec backend python scripts/regenerate_distractors.py --status
```

## Обновление до новой версии

```bash
cd /opt/rst
git pull
docker compose --env-file deploy/.env up -d --build
```

Базы при этом не трогаются — они лежат в `data/` на хосте, отдельно от контейнеров.
Недостающие колонки в таблицах backend доберёт сам при старте (`run_migrations()`).

Если обновились вопросы — после `git pull` ещё раз прогоните импорт (шаг 6).

Откатиться на предыдущую версию, если что-то сломалось:

```bash
git log --oneline -5          # найти хеш рабочего коммита
git checkout ХЕШ
docker compose --env-file deploy/.env up -d --build
```

## Бэкапы — что именно хранить

Всё ценное — в одном каталоге `/opt/rst/data`:

- `rst.db` — банк вопросов (источник истины);
- `rst_web.db` — пользователи сайта, история тестов, статистика;
- `backups/` — автоматические снимки базы сайта за последние 14 дней.

Снимки на том же сервере не спасают от потери самого сервера, поэтому забирайте копию
на Mac — например раз в неделю:

```bash
scp -r user@СЕРВЕР:/opt/rst/data ~/rst-backup-$(date +%F)
```

Восстановление: остановить контейнеры (`docker compose down`), положить нужный файл на место
`data/rst_web.db`, вернуть права (`sudo chown -R 10001:10001 /opt/rst/data`) и поднять
обратно.

Порядок действий при утечке персональных данных, со сроками уведомления по правилам РК —
в [SECURITY_INCIDENT.md](SECURITY_INCIDENT.md).

## Локальная проверка сборки без домена

Если хочется убедиться, что всё собирается, ещё до покупки домена — поставьте в
`deploy/.env`:

```
SITE_ADDRESS=:80
```

Тогда Caddy не станет запрашивать сертификат и отдаст сайт по `http://IP-СЕРВЕРА`.
Это только для проверки: HTTPS нет, наружу так работать нельзя. В этом режиме переменная
`CORS_ORIGINS` собирается из `SITE_ADDRESS` и получается бессмысленной — на локальную
проверку это не влияет, но задайте её явно, если будете подключать мобильное приложение.

## Частые проблемы

- **Сайт не открывается, в логах `web` ошибки получения сертификата.** Почти всегда DNS:
  A-запись ещё не доехала или указывает не на тот IP. Проверьте `dig +short ВАШ_ДОМЕН` —
  должен вернуться IP сервера. Также убедитесь, что порты 80 и 443 открыты в файрволе:
  Let's Encrypt проверяет домен, обращаясь к серверу извне.

- **`backend` перезапускается, в логах `unable to open database file` или
  `readonly database`.** Не выставлены права на каталог с базами. Выполните
  `sudo chown -R 10001:10001 /opt/rst/data` и `docker compose restart backend bot`.

- **Сайт открывается, но в списке нет ни одного вопроса.** Не выполнен шаг 6 либо на сервер
  не скопирован `data/rst.db` (шаг 3). Проверьте, что файл на месте: `ls -la /opt/rst/data`.

- **Бот не отвечает.** `docker compose logs bot`. Обычно неверный или пустой `BOT_TOKEN`
  в `deploy/.env`. После правки файла — `docker compose --env-file deploy/.env up -d`.

- **Письма не приходят.** Для Gmail нужен именно
  [App Password](https://myaccount.google.com/apppasswords), не обычный пароль от аккаунта.
  Плюс лимит ~500 писем в день.

- **ИИ-ассистент отвечает ошибкой.** Либо не задан `GEMINI_API_KEY`, либо на сегодня
  исчерпана бесплатная квота (~20 запросов на весь проект, общая с ночной генерацией
  дистракторов). Квота обновляется на следующие сутки.

- **`docker compose` жалуется на переменные вида `нужен SECRET_KEY`.** Забыт `--env-file
  deploy/.env` в команде, либо соответствующая строка в файле осталась пустой.

- **Кончилось место на диске.** Старые образы Docker накапливаются при каждой пересборке.
  Очистить: `docker system prune -af`. Данные в `data/` эта команда не трогает.
